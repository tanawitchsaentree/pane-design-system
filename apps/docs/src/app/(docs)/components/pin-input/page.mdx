# PinInput

PinInput is a row of single-character cells for OTP/verification codes. It's the most complex
component in this wave — real client state plus effects (`"use client"`), and bespoke
focus-routing logic written by hand rather than borrowed from a behavior library, since no
existing Radix/React Aria primitive models "N linked single-character cells." Use it for
verification-code entry flows (SMS OTP, email confirmation codes).

```tsx
import { PinInput } from 'dial-react';
```

## Composition

`onComplete` fires once the value reaches `length` characters — the hook for submitting a code
automatically instead of waiting for an explicit submit action.

## Accessibility

**Keyboard:** Typing a character auto-advances focus to the next cell. Backspace on a cell with a
value clears just that cell (no focus move); Backspace on an already-empty cell clears and moves
focus to the previous cell. ArrowLeft/ArrowRight move focus between cells without altering any
value. All of this is covered by dedicated tests in `PinInput.test.tsx`, including the
auto-advance-on-type, backspace-clears-vs-backspace-moves distinction, and arrow-key focus movement
(unlike Radio's arrow-key behavior, this logic is component-implemented, not native, so it is
directly unit-testable in jsdom).

**Screen reader:** The root has `role="group"` with the caller-supplied `aria-label` as its
accessible name; each cell additionally exposes `aria-label="Digit N of length"` so a screen
reader announces cell position, and `invalid` sets `aria-invalid="true"` on every cell.
`inputMode="numeric"` plus a `pattern` hint the on-screen keyboard without blocking other
assistive input methods.

**Focus:** Each cell is a real, independently focusable native `<input maxLength=1>`; there is no
hidden/decorative layer as in Checkbox/Radio/Switch — the visible cell IS the focus target, sized
per the `size.control.*` scale via `data-size`.

## Related

- `Input` — shares the `size.control.*` scale and `invalid` convention, though PinInput's cell
  layout and focus-routing are entirely bespoke.
- `FormField` — can wrap a PinInput for a labeled/helper-text field, though `FormField`'s
  `cloneElement` wiring targets a single control's `id`/`aria-describedby`, so pairing needs the
  same care as with any multi-part control.
