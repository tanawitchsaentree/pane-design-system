- **ตัวเลือกที่ตัดทิ้ง:** ข. Hybrid (ยืม 2-accent orange+mint จากภาพ 3 มาคู่กับโครง Braun), ค. Feel ล้วน (ภาพ 3 เป็น driver หลัก ภาพ 1-2 เป็น archive)
- **กระทบ:** color.action.* (สงวนสีจัดไว้จุดเดียว ห้ามมี secondary accent สีมินต์), type scale (แบน ratio ต่ำ ~1.2), density baseline (comfortable/spacious จาก ref ที่ของน้อยชิ้น), ไม่มี texture/speckle token · ถ้าทีหลังอยากดึงภาพ 3 กลับมา = supersede ตัวนี้ + เพิ่ม secondary accent hue และพิจารณา texture token ใหม่

### D-002: Platform = Web-first
- **วันที่:** 2026-08-08 · **Phase:** 1 (ข้อ 0)
- **เลือก:** web-first — hover เป็น interaction ชั้นหนึ่ง (ไม่ใช่แค่ enhancement), touch target ไม่บังคับ 44px เป็นกฎตายตัวแต่ยังคงเผื่อ 40px ขั้นต่ำสำหรับ mouse+trackpad, density default = comfortable (ยืนตาม D-001), breakpoint แรกที่ล็อก = desktop/laptop viewport (lg 1024) ก่อน แล้วไล่ลงมือถือทีหลังแบบ responsive ปกติ ไม่ใช่ mobile-first reflow, ลำดับ component inventory ยืนตาม default (Sidebar/ContextMenu/hover-Tooltip ไม่ต้องเลื่อนไปท้าย, ไม่ดัน BottomNav/Sheet ขึ้นก่อน)
- **เพราะ:** user ตอบ "web" ตรงคำถามข้อ 0 ของ Phase 1
- **ตัวเลือกที่ตัดทิ้ง:** mobile-first (touch target 44px บังคับ, hover เป็น enhancement เท่านั้น, breakpoint แรก 390), both-equal (ต้องออกแบบคู่ขนานทั้ง input mode ตั้งแต่ต้น)
- **กระทบ:** ลำดับ component inventory (คง default tier ไม่ reorder), qa-a11y checklist (ไม่ต้องบังคับ hover-only ต้องมี tap/focus fallback อย่างเข้มเหมือน mobile-first แต่ยัง WCAG keyboard-focus ปกติ), ทุก breakpoint token (lg เป็น anchor แรก), docs/lab preview default เปิดที่ desktop frame

### D-003: Spacing base unit = 8px
- **วันที่:** 2026-08-08 · **Phase:** 1
- **เลือก:** base unit = 8px · scale = 0, 8, 16, 24, 32, 40, 48, 64, 80, 96, 128, 160 (คูณ 8 ทั้งหมด) · semantic alias: inset.sm/md/lg, stack.sm/md/lg, inline.sm/md/lg ผูกกับ scale นี้
- **เพราะ:** ref (Braun radio, D-001) ไม่มีตัวเลขที่วัดได้ตรงเพราะเป็น hardware แต่ layout ที่เห็น (speaker ใหญ่, dial ใหญ่, ปุ่มห่างกันชัด, ของน้อยชิ้นไม่แน่น) ส่อ mood spacious/comfortable ซึ่งจับคู่กับ base 8 มากกว่า 4 (4 เหมาะ dense UI/dashboard ที่ระบบนี้ยังไม่ระบุว่าต้องมี) — user ยืนยัน 8
- **ตัวเลือกที่ตัดทิ้ง:** 4px (granularity ละเอียดกว่า เผื่อ dense component ในอนาคต แต่ over-engineer ตอนนี้), 6px (หารลงตัวกับ grid/breakpoint มาตรฐานยาก)
- **กระทบ:** space.* ทั้งหมด, size.* (ยังคนละ namespace แต่มักอ้าง dimension เดียวกับ space — ต้องเช็คตอน sizing round), ทุก component token ที่อ้าง dimension, grid gutter · ถ้าทีหลังต้องมี dense component (table แน่นๆ) = supersede ตัวนี้หรือเพิ่ม exception scale ย่อยเฉพาะจุด

### D-004: Sizing scale — control height หนาแบบ Braun (md=48)
- **วันที่:** 2026-08-08 · **Phase:** 1
- **เลือก:** `size.icon.*` = 16/20/24/32 · `size.avatar.*` = 24/32/40/48/64/96 · `size.control.*` (t-shirt) = sm 40 · md **48** · lg 56 · xl 64 (คนละ namespace จาก `space.*` ตาม D-003 เด็ดขาด แม้ค่าจะซ้ำ 8-multiple)
- **เพราะ:** user สั่ง "auto approve ให้ใกล้เคียงตามภาพเลย" — เลือกทางเลือกที่ขยับ control height ทั้งชุด +8 จาก default มาตรฐาน เพราะ dial/knob ในภาพ Braun มีสัดส่วนหนา มั่นคง ใหญ่กว่า flat UI ทั่วไปเทียบตัวเครื่อง ไม่ใช่ค่า default เฉยๆ
- **ตัวเลือกที่ตัดทิ้ง:** default มาตรฐาน (sm32/md40/lg48/xl56) — บางเกินไปเทียบสัดส่วนหนาของ ref
- **กระทบ:** ทุก component ที่ใช้ t-shirt sizing (Button, Input, Select, ฯลฯ), component tokens ที่อ้าง `size.control.*`, ต้องเช็ค touch/click target ยังพอเหมาะกับ web-first (D-002 ไม่บังคับ 44px แต่ md=48 เกินอยู่แล้วไม่มีปัญหา) · ถ้าทีหลังอยากได้ UI บางลง = supersede ตัวนี้กลับไป default

### D-005: Typography — base 16px, ratio แบน 1.2 (Minor Third), เดี่ยว font family
- **วันที่:** 2026-08-08 · **Phase:** 1
- **เลือก:** base 16px · ratio 1.2 → scale: xs 11 · sm 13 · md 16(base) · lg 19 · xl 23 · 2xl 28 · 3xl 33 · 4xl 40 · 5xl 48 · font stack เดียวกันทั้ง heading/body (geometric grotesque sans เช่น Inter/system-ui — web-safe stand-in ของ geometric sans แบบ Braun) + mono แยกสำหรับ code · line-height: body 1.5, heading 1.15
- **เพราะ:** D-001 กำหนดไว้แล้วว่า hierarchy มาจากตำแหน่ง/ขนาด block ไม่ใช่ font scale (ref: FM display, VOLUME label ใช้ weight/family เดียวกันหมด ไม่มี type ใหญ่เด่น) → ratio ต้องแบนที่สุดในตารางมาตรฐาน (1.2) ไม่ใช้ 1.25+ ที่จะสร้าง hierarchy ทางฟอนต์ซึ่งขัดกับ DNA ของ ref
- **ตัวเลือกที่ตัดทิ้ง:** ratio 1.25 (Major Third — สมดุลทั่วไป แต่สร้าง hierarchy ทางฟอนต์มากกว่าที่ ref บอก), 2 font families แยก heading/body (ref ไม่มีสัญญาณว่าต้องแยก)
- **กระทบ:** text.* composite tokens ทั้งหมด, ทุก component ที่ใช้ heading/body, ถ้าทีหลังอยากได้ hierarchy จากฟอนต์มากขึ้น = supersede ratio และอาจต้องเพิ่ม font family ที่สอง

### D-006: Color — neutral ramp จาก cream, accent orange สงวนจุดเดียว
- **วันที่:** 2026-08-08 · **Phase:** 1
- **เลือก:** `color.neutral.*` ramp 50-950 เป็น warm neutral (ไม่ใช่ gray เย็น) จาก cream (~#F2EFE9 ที่ 50) ไปมืดใกล้ดำอมน้ำตาล (~#242220 ที่ 950) generate ใน OKLCH · `color.brand.*` (accent) = orange/coral ramp จากภาพ knob · roles อื่น (success/warning/danger/info) ใช้ hue มาตรฐานแต่ desaturate ลงให้เข้ากับ mood สงบ · semantic: `bg.canvas`=neutral.50, `bg.surface`=neutral.0/25, `text.default`=neutral.900, `action.primary`=brand.600 · **กฎสงวนสี (จาก D-001):** accent เข้มใช้เฉพาะ primary interactive element ที่สำคัญที่สุดของแต่ละ view ห้ามใช้ตกแต่ง/เน้นข้อความทั่วไป
- **เพราะ:** ตัวเครื่อง ref เป็น cream ล้วน สีจัดอยู่แค่ปุ่มหมุนเดียว — สื่อชัดว่า neutral ramp ต้องอุ่น (warm) ไม่ใช่ gray เย็นแบบ tech-neutral ทั่วไป และ accent ต้อง scarce ตามกฎที่ lock ไว้แล้วใน D-001
- **ตัวเลือกที่ตัดทิ้ง:** cool/gray neutral ramp (มาตรฐานทั่วไปแต่ขัดกับ warm cream ของ ref), multi-accent (primary+secondary) — ขัด D-001 ตรงๆ
- **กระทบ:** color.* ทั้งหมด, ทุก semantic bg/text/border/action token, contrast AA ต้องคุมเข้มเพราะ warm neutral มักมี contrast ต่ำกว่า cool gray ที่ lightness เดียวกัน ต้อง QA เช็คละเอียด · ถ้าทีหลังอยากได้ 2nd accent = supersede D-001 ก่อน (impact ใหญ่กว่าตัวนี้)

### D-008: Radius / Shadow / Border — soft radius, ไม่มี decorative shadow, hairline แทนเงา — **SUPERSEDED-BY D-029 (2026-08-13)**
- **วันที่:** 2026-08-08 · **Phase:** 1
- **เลือก:** radius scale sm8/md12/lg16/xl24/2xl32/full (soft-rounded ตามตัวเครื่อง ไม่ sharp ไม่ pill-only) · **ห้ามมี drop-shadow ตกแต่งบน card/button/input ปกติ** — ใช้ `border.hairline` (1px, neutral.200-300) แทนเงาเป็นตัวสร้างขอบ/definition · shadow (elevation) สงวนไว้เฉพาะ layer ที่ต้อง "ลอยจริง" เท่านั้น (modal, popover, toast) ระดับ 0-2 เบาๆ ไม่ใช่เงาหนัก · border widths 1/2

- **ตัวเลือกที่ตัดทิ้ง:** sharp radius (ขัดกับตัวเครื่องโค้งมน), neumorphism dual-shadow (มี recipe อยู่แล้วแต่ขัดกับกฎ "ไม่มี drop-shadow ตกแต่ง" ของ D-001 ตรงๆ)
- **กระทบ:** radius.*, shadow.* (จำกัดการใช้เหลือ elevation จริงเท่านั้น), border.hairline ต้องมีในทุก interactive component, qa-a11y ต้อง verify ว่า state เปลี่ยนด้วย non-shadow cue เสมอ (ดู style recipe)

### D-010: Density baseline = Comfortable
- **วันที่:** 2026-08-08 · **Phase:** 1
- **เลือก:** density default = **comfortable** (ยืนยันเป็นทางการจาก note ที่ตั้งไว้ใน D-001) — เผื่อ compact/spacious mode ไว้ในโครง token แต่ยังไม่ generate จนกว่ามี use case จริง (เช่น dashboard/table หนาแน่น)
- **เพราะ:** ref แสดงของน้อยชิ้น โล่ง ไม่มีสัญญาณว่าต้อง dense ตั้งแต่ต้น — comfortable ตรงกับ mood ที่สุดและไม่ over-engineer ตอนยังไม่รู้ scope ของ dense component
- **ตัวเลือกที่ตัดทิ้ง:** compact (ไม่มีหลักฐานรองรับ ต้องรอ use case), spacious (เผื่อไว้เกินความจำเป็นตอนนี้)
- **กระทบ:** space.* mapping ที่ compact/spacious mode จะสลับ (โครงเผื่อไว้แต่ยังไม่ generate ค่า), ต้อง revisit ทันทีที่มี component ที่ต้องการ dense จริง

### D-013: W2 Atoms-Core — auto-approve API ตาม pattern มาตรฐาน (Text/Heading/Icon/Button/IconButton/Link/Badge/Avatar/Spinner/Skeleton/Kbd/Image)

- **เพราะ:** user ชี้ตรงตาม ARIA Authoring Practices Guide — combobox widget มี `aria-autocomplete` เป็น attribute ของตัวมันเอง (none/list/both) ไม่ใช่ widget คนละตัว ทำแยกกันจะได้ 2 component ที่ API ซ้อนทับ 90% ต่างกันแค่ prop เดียว ตรงกับที่ Reuse Check (component-engineer.md ข้อ 0) ควรจับได้ตั้งแต่แรกถ้าทำ W5 แบบ auto-approve
- **ตัวเลือกที่ตัดทิ้ง:** ทำ Autocomplete แยกเป็น component อิสระ (ตามที่ catalog เดิมเขียนไว้) — ตัดทิ้งเพราะจะสร้าง pattern drift ทันทีที่ wave นี้เริ่ม (สองตัวที่ทำหน้าที่เดียวกันแต่คนละ API)
- **กระทบ:** `docs/CATALOG.md` ต้องอัพเดตจำนวนรวม (104→103) และรายชื่อ W5 (10→9 ตัว) · Combobox ต้อง design API ให้รองรับ `autocomplete: 'none'|'list'|'both'` ตั้งแต่ BATCH API REVIEW ของ wave นี้ ไม่ใช่เติมทีหลัง

### D-023: เกณฑ์เลือก behavior engine (Radix vs React Aria vs native) — lock ก่อนสร้างตัวที่เหลือของ W5
- **วันที่:** 2026-08-09 · **Phase:** 3 (Wave 5, ระหว่าง Listbox checkpoint)
- **เลือก:** เกณฑ์ 4 ข้อ เรียงตามลำดับเช็ค (เจอข้อไหนก่อนใช้ข้อนั้น ไม่ต้องเช็คข้อถัดไป):
  1. **Native HTML form control พอเองไหม** — ถ้า pattern ทำได้ด้วย native `<input type=radio>`/`checkbox` ที่ group กันด้วย `name` (browser จัดการ roving focus ให้ฟรีอยู่แล้ว ตามที่ Radio/Checkbox/Switch พิสูจน์แล้วจาก D-016) → ใช้ native ห่อด้วย custom visual เท่านั้น ไม่ต้อง engine dependency เลย — ถูกที่สุดและ robust ที่สุด
  2. **Radix มี dedicated primitive สำหรับ ARIA pattern นี้ตรงๆ ไหม** (เช็คจริงด้วย `npm view` ไม่ใช่เดา — วิธีที่ยืนยันว่า Listbox ไม่มี bare primitive คือเช็คแบบนี้) → ถ้ามี ใช้ Radix ต่อจาก Wave 4 (Dialog/Popover/Tooltip/Toast ใช้อยู่แล้ว) เพื่อไม่เพิ่ม engine ใหม่โดยไม่จำเป็น
  3. **Core behavior คือ collection ของ item ที่เลือกได้ (roving tabindex ข้ามหลาย item + typeahead + multi-select + scroll)** และ Radix ไม่มี primitive แยกให้ (bundle อยู่ใน Select อย่างเดียว ไม่ export standalone) → ใช้ React Aria's collection stack (`@react-stately/list`/`@react-aria/listbox`/`combobox`/`tag` ตามแต่ family) — ทุกตัวที่เข้าเกณฑ์นี้ **ต้อง reuse `_roving-focus.ts` helper ของ Listbox** ไม่ fork ใหม่ (ตาม roving-focus.md)
  4. **ห้ามผสม engine ในตัวเดียวกัน** — ถ้า component ต้องมีทั้ง overlay (open/dismiss/positioning/focus-trap) และ collection (listbox ข้างใน) ต้องเลือก engine เดียวที่ครอบทั้งคู่ ไม่ใช่เอา Radix Popover มาห่อ React Aria's listbox (หรือกลับกัน) — เหตุผล: จะได้ seam ของ keyboard contract ตรงจุดเชื่อม (เช่น Escape จะไปเข้า handler ไหนก่อน, focus-restore ใครจัดการ) React Aria มี overlay hooks ของตัวเอง (`@react-aria/overlays`) ที่ทำงานร่วมกับ collection stack ได้ไร้รอยต่อกว่า
- **ผลตัดสินของ W5 ที่เหลือ (lock ไว้ล่วงหน้า กันเลือกตามสะดวกทีละตัว):**
  - **Select, Combobox (รวม autocomplete mode ตาม D-022), MultiSelect** — เข้าเกณฑ์ข้อ 3 (listbox-family ข้างใน, Radix ไม่มี bare primitive) → **React Aria ทั้งหมด** (`@react-aria/select`, `@react-aria/combobox`, หรือ Listbox ตัวเดิมกับ `selectionMode="multiple"`) รวม popover positioning ก็ใช้ React Aria's overlay hooks (ไม่ใช่ Radix Popover) ตามเกณฑ์ข้อ 4 — reuse Listbox's `Listbox.Item`/`_roving-focus.ts` เป็นฐานเดียวกัน
  - **RadioCards, Rating** — เข้าเกณฑ์ข้อ 1 (เป็น "เลือก 1 จาก N" ที่ native radio-group ทำได้เอง ไม่มี custom keyboard model ที่ native ให้ไม่ได้) → **native `<input type=radio>` grouped by `name`** ห่อด้วย custom visual (การ์ด/ดาว) ตาม pattern เดียวกับ Radio component เดิม — ไม่ใช่ Radix หรือ React Aria — ถ้า Rating ต้องการ continuous/half-star input ทีหลัง (เกินความสามารถ native radio) ต้องกลับมา revisit decision นี้ก่อนสร้าง ไม่ใช่เดาเปลี่ยนกลางทาง
  - **TagInput** — เข้าเกณฑ์ข้อ 3 สองชั้น (suggestion dropdown = listbox-family, tag pill list ที่ลบได้ = collection ที่มี arrow-nav+backspace-remove ของตัวเอง) → **React Aria ทั้งคู่** (Combobox engine สำหรับ suggestion popup, TagGroup pattern สำหรับ pill list — เช็คจาก `@react-aria/tag` ก่อนสร้างจริงว่ามีเวอร์ชันที่ resolve ได้ตรงกับ React Aria เวอร์ชันที่ pin ไว้ใน Listbox)
  - **Menu/Dropdown, ContextMenu** — เข้าเกณฑ์ข้อ 2 (Radix มี `@radix-ui/react-dropdown-menu`/`@radix-ui/react-context-menu` ตรงๆ, `role="menuitem"` เป็น command-pattern ไม่ใช่ selection-pattern) → **Radix** ต่อจาก Wave 4 — ยืนยันอีกครั้งตามที่คุยไว้แล้วว่าห้าม import `_roving-focus.ts` ของ Listbox เด็ดขาด (คนละ ARIA pattern จริง)
- **เพราะ:** ระบบเพิ่งมี 2 engine พร้อมกัน (Radix จาก Wave 1-4, React Aria จาก Listbox) — ถ้าไม่ lock เกณฑ์ล่วงหน้า ตัวถัดๆ ของ W5 จะเลือกตามความสะดวกของแต่ละรอบสร้าง (เช่น component-engineer subagent คนละ session อาจเลือกคนละอย่างสำหรับ pattern เดียวกัน) ผลคือ keyboard contract ไม่ตรงกันระหว่าง component ที่ควรจะ "รู้สึกเหมือนกัน" (เช่น Select vs MultiSelect ควร Arrow/Home/End/typeahead แบบเดียวกันเป๊ะ) และ bundle ซ้อนโดยไม่จำเป็น (ถ้าบาง component ดึง Radix มาทำสิ่งที่ React Aria ทำอยู่แล้วในระบบ)
- **ตัวเลือกที่ตัดทิ้ง:** ปล่อยให้ component-engineer เลือก engine เองทีละตัวตาม judgment ของรอบนั้น (ตัดทิ้งเพราะเป็นสาเหตุของปัญหาที่เกณฑ์นี้กำลังป้องกัน) · ใช้ React Aria ล้วนทั้งระบบรวม Wave 1-4 ที่ทำไปแล้ว (ตัดทิ้งเพราะต้อง retrofit ย้อนหลัง 39 component ที่ผ่าน QA แล้ว ไม่ต่างจาก D-020 ที่ปฏิเสธ Portable Core retrofit ไปแล้วด้วยเหตุผลเดียวกัน)
- **กระทบ:** Select/Combobox/MultiSelect/TagInput ต้องติดตั้ง React Aria package เพิ่มตาม family ที่ใช้ (ดูรายการ resolved version ที่ Listbox pin ไว้ใน `packages/react/package.json` เป็นฐาน ไม่ pin เวอร์ชันใหม่แยกที่ชนกัน) · RadioCards/Rating ไม่ต้องพึ่ง engine ใหม่เลย (เบาที่สุดใน wave) · ถ้าทีหลังพบว่า React Aria's overlay hooks ไม่พอสำหรับ positioning ที่ Select/Combobox ต้องการ (เช่น edge-case ที่ Popover ของ Wave 4 เจอและมี TODO ค้างอยู่ใน `w4-popover-positioning.spec.ts`) ต้องกลับมา supersede decision นี้เฉพาะจุด ไม่ใช่เปลี่ยน engine ทั้ง component

### D-024: API Vocabulary Contract — Collection vs Standalone Control, ภาษาเป็นของ Dial ไม่ใช่ของ engine
- **วันที่:** 2026-08-09 · **Phase:** 3 (Wave 5, ก่อนเปิดสายการผลิต 6 ตัวที่เหลือ)
- **เลือก:** สอง prop vocabulary ตายตัว แยกตาม component category (ไม่ใช่ตาม engine ที่อยู่ข้างใน):
  1. **Collection** (Listbox, Select, Combobox, MultiSelect, Menu/Dropdown, ContextMenu, TagInput's suggestion list) — ใช้ `selectedKeys` / `defaultSelectedKeys` / `onSelectionChange` / `disabledKeys` เสมอ ไม่ว่า engine ข้างในจะเป็น React Aria (คืนชื่อพวกนี้ให้อยู่แล้ว — ไม่ต้องแปล) หรือ Radix (Menu/Dropdown/ContextMenu ใช้ `@radix-ui/react-dropdown-menu` ซึ่งมีชื่อ prop ของตัวเอง เช่น `onValueChange`/`checked` ต่อ item — **ต้องห่อให้พูดภาษานี้แทน**)
  2. **Standalone control** (Input, Textarea, Checkbox, Radio, Switch, PinInput, Rating, RadioCards) — ใช้ `value`/`defaultValue`/`onChange` (text-like) หรือ `checked`/`defaultChecked`/`onChange` (boolean-like) ตามที่ W2/W3 ทำไว้แล้ว — ไม่เปลี่ยน
  - **เกณฑ์แยกสองกลุ่ม:** Collection คือ component ที่เลือกได้ "หลาย item จาก set ที่มี identity เป็น key" (มี concept ของ "value ไหนคือ key ของ item ไหน") — Standalone control คือ component ที่มี "ค่าเดียว" ไม่มี collection ของ item ให้เลือกจาก
- **ผลตรวจย้อน W2/W3 (ตามที่ user สั่งให้ list มาก่อนแก้):** **ไม่พบตัวไหนพูดคนละภาษา** — Input/Textarea/PinInput ใช้ `value`+`onChange` ตรงกันหมด, Checkbox/Radio/Switch ใช้ `checked`+`onChange` ตรงกันหมด (native input vocabulary, ไม่ผ่าน engine ไหนเลยเพราะเป็น native form control ตาม D-016), W4 overlays (Dialog/Drawer/Popover/Tooltip/Toast) ใช้ `onOpenChange` ตรงกันหมดแม้ Radix ให้ชื่อนี้มาตรงๆ อยู่แล้ว — **W2/W3/W4 สะอาดทั้งหมด ไม่มีงานย้อนหลังต้องแก้**
- **เพราะ:** ตอนนี้มี 2 engine ในระบบ (Radix, React Aria) ถ้าไม่ lock ว่า public API พูดภาษาของ Dial เสมอ (ไม่ใช่ leak ชื่อ prop ของ engine ตรงๆ) ผลคือ caller ต้องรู้ว่า component ไหนใช้ engine ไหนถึงจะเดา prop name ถูก และถ้าเปลี่ยน engine ทีหลัง (เช่น Menu ย้ายจาก Radix ไป engine อื่น) จะเป็น breaking change ที่ไม่ควรเป็น breaking change ในระดับ public API
- **ตัวเลือกที่ตัดทิ้ง:** ให้แต่ละ component ใช้ prop name ตาม engine ของตัวเอง (Radix component ใช้ชื่อ Radix, React Aria component ใช้ชื่อ React Aria) — ตัดทิ้งเพราะเป็นสาเหตุของปัญหาที่ decision นี้ป้องกัน (caller ต้องเดาคนละชื่อสำหรับ pattern ที่ "รู้สึกเหมือนกัน")
- **กระทบ:** Menu/Dropdown, ContextMenu (Radix-based ตาม D-023) ต้องเขียน adapter layer แปลง Radix's `onValueChange`/per-item `checked` ให้ออกมาเป็น `selectedKeys`/`onSelectionChange`/`disabledKeys` ที่ public API — เพิ่มงานเล็กน้อยตอนสร้าง 2 ตัวนั้น แต่ทำให้ caller เขียน Select/Menu/MultiSelect ด้วย vocabulary เดียวกันทั้งหมด

### D-025: Card root border = `color.border.interactive` แทน `color.border.hairline` (WCAG 1.4.11 fix ก่อน publish 0.1.0)
- **วันที่:** 2026-08-10 · **Phase:** Pre-publish review (ก่อน publish 0.1.0)
- **เลือก:** เปลี่ยน `card.json`'s `root.border` จาก `{color.border.hairline}` เป็น `{color.border.interactive}` — token เดียวกับที่ Button outline/Input/Checkbox/Radio ใช้อยู่แล้วสำหรับ boundary จริง (D-014) วัด contrast ได้ 3.72:1 (light) / 3.72:1 (dark) บน `surface.canvas` ผ่าน WCAG 1.4.11's 3:1 UI-boundary minimum ทั้ง 2 theme · header/footer internal divider ยังอยู่ที่ `border.hairline` เดิม (เป็นเส้นแบ่งภายในการ์ดที่ตั้งตัวแล้ว ไม่ใช่ขอบการ์ดกับหน้า ไม่เข้าเกณฑ์ 1.4.11 แบบเดียวกัน)

- **กระทบ:** `packages/tokens/src/component/card.json` (`root.border`), `packages/react/src/components/Card/Card.module.css` (doc comment แก้ให้ตรง + comment อธิบายว่า hover ไม่เปลี่ยนสี border อีกต่อไปเพราะ resting/hover ใช้ token เดียวกันแล้ว), `packages/spec/card.md` (บรรทัด 6 และ 26 แก้ให้ตรงกับ token ใหม่) · `system/EXCEPTIONS.md` อัพเดต note อธิบายว่าทำไม Card ไม่เข้าเกณฑ์ E-001 · จำนวน exception เปิดของระบบไม่เปลี่ยน (ยังคง 1 = E-001) เพราะนี่คือการแก้บั๊ก ไม่ใช่การขึ้นทะเบียนข้อยกเว้นใหม่ · gate สุดท้ายที่ verify แล้ว: lint 0/232, tsc 0 error, vitest 360/360 — ไม่มี regression

### D-026: box-sizing: border-box บน hover-border-widen elements (7 component) + Switch reduced-motion override (external audit fix, ไม่แตะ token/vector/lineage decision ใดๆ)

- **ตัวเลือกที่ตัดทิ้ง:** ยกเลิก D-008 ทั้งหมด อนุญาต shadow ทุกที่ (ตัดทิ้งเพราะจะเปิดช่องให้ float-everything ซึ่งขัดกับ mood สงบของ D-001 — เขียนกฎแยกหน้าที่ให้ชัดแทนเพื่อไม่ให้ agent ในอนาคตอ่านเป็น "อนุญาตแล้ว" เฉยๆ) · เขียนเป็น exception ใหม่ใน EXCEPTIONS.md แทนการ supersede (ตัดทิ้งเพราะนี่ไม่ใช่การยอมรับค่าที่ตกเกณฑ์ — เป็นการเปลี่ยนกฎเองตามคำสั่ง user ตรงๆ, exception registry สงวนไว้สำหรับกรณี "ยอมรับสิ่งที่ตกเกณฑ์" ไม่ใช่ "เปลี่ยนเกณฑ์")
- **กระทบ:** `docs/style-recipes/braun-flat.md` rule 1 (ต้องแก้ข้อความให้ตรงกับกฎใหม่ — "no decorative shadow" ยังจริง แต่ต้องเพิ่มข้อยกเว้น structural) · **`system/EXCEPTIONS.md`'s E-001 ต้อง re-check**: scope เดิมเขียนไว้ว่า "shadow ถูกแบนทั้งระบบยกเว้น floating layer" เป็นสมมติฐานพื้นหลังของ E-001 (accent bar <3:1) — E-001 เองไม่ได้พูดเรื่อง shadow ตรงๆ (พูดเรื่อง border/accent-bar contrast) จึง**ไม่กระทบ E-001 โดยตรง** แต่บันทึกไว้ว่าได้ re-check แล้วตามที่ order สั่ง (`<supersede-protocol>`: "E-001's scope may no longer apply once shadows are functional rather than banned" — ตรวจแล้วพบว่า E-001 ไม่ได้ผูกกับกฎ shadow-ban เลย เป็นคนละเรื่อง, EXCEPTIONS.md ไม่ต้องแก้) · `packages/tokens` ต้องมี `shadow.raised.*`/`shadow.inset.*` ใหม่ (ดู token task ถัดไปในรอบนี้) · qa-a11y ต้องเพิ่มเช็ค G-F1 (recipe markers, ดู `.claude/skills/form-language/references/gates.md`) เป็นส่วนหนึ่งของ gate ปกติ ไม่ใช่แค่ advisory อีกต่อไป เพราะตอนนี้มี component จริงให้ทดสอบ (Gate Proof ได้จริงเป็นครั้งแรก)
